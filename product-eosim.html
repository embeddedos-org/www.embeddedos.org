EoSim — Embedded Systems Simulator

EoSim is the EoS simulator — a unified harness over QEMU, Renode, and a hardware-in-the-loop bridge that lets you boot, debug, and CI-test EoS firmware against 52+ virtual platforms without touching real silicon.

Overview

What EoSim is

EoSim wraps QEMU and Renode behind a single Python API and CLI: pick a platform, hand it an EoS firmware image, and you get an inspectable virtual board with simulated peripherals, a GDB stub, and scriptable scenarios.

For tests that demand real hardware, the HIL bridge proxies the same API onto attached reference boards — so the same scenario runs in CI on a virtual STM32 and on a physical board on an engineer's desk.

The shape of EoSim at a glance.

STM32 family, NXP i.MX, ESP32, RISC-V SiFive, ARM Cortex-A SoCs, x86_64 servers, and more.

Three execution backends behind one API; switch with a flag.

Scriptable Scenarios

Drive peripherals, inject faults, advance time — all in Python.

▣

GDB & Trace Hooks

Built-in GDB stub, full instruction trace, and EoS kernel-aware introspection.

▣

CI Integration

Runs in GitHub Actions / GitLab / Jenkins; produces JUnit-format results.

▣

Fault Injection

Bit-flip, brown-out, broken-peripheral scenarios for resilience tests.

▣

Multi-Node

Networks of simulated boards share a virtual bus / Ethernet / Wi-Fi.

▣

Benchmarks

Same harness drives perf / power benchmarks — exports to CSV and Plotly.

▣

Hardware-in-the-Loop

Same scenarios run on physical reference boards via the HIL bridge.

Architecture

EoSim Simulator Architecture

The virtual world (QEMU backend, virtual peripherals, GDB remote debugger, coverage tracing, fault injection) connected to the real hardware world through the HIL bridge with sub-microsecond latency.

EoSim at a Glance

Simulation BackendQEMU 8.x with EoS-specific machine models
HIL Bridge Latency< 1 µs virtual-to-real peripheral round-trip

Quick Start

Running EoS in the Simulator

ShellQuick Start
# 1. Build for the virtual Cortex-M4 target
ebuild build --profile cortex-m4-qemu

# 2. Launch EoSim (opens QEMU + GDB server on :1234)
eosim run build/firmware.elf --profile cortex-m4-qemu

# 3. In another terminal: connect GDB
arm-none-eabi-gdb build/firmware.elf \
  -ex "target remote :1234" \
  -ex "monitor reset halt" \
  -ex "continue"

# 4. Run with fault injection (simulate flash write failure)
eosim run build/firmware.elf \
  --fault flash_write_error:0x08010000:50%

# 5. Collect coverage report
eosim run build/firmware.elf --coverage
eosim coverage-report --format lcov --output coverage/

# 6. HIL mode: bridge virtual UART to real hardware
eosim run build/firmware.elf \
  --hil uart0:/dev/ttyUSB0:115200

EoSim requires QEMU 8.x. Install with: ebuild install-deps --sim

Applications

Where EoSim Is Used

🧪

Hardware-Free Development

Develop and test firmware before hardware is available, enabling parallel hardware and software development tracks.

🔄

CI/CD Regression Testing

Run the full firmware test suite in QEMU on every commit — no physical hardware required in the CI pipeline.

💥

Fault Injection Testing

Simulate power loss, flash corruption, and peripheral failures to validate error-handling and recovery code paths.

📊

Coverage Analysis

Achieve > 90% branch coverage on embedded firmware using EoSim's instrumented execution mode.

🔌

HIL Testing

Bridge simulated firmware to real sensors and actuators through the HIL interface for mixed virtual/physical testing.

🎓

Education & Training

University embedded systems courses use EoSim to teach RTOS concepts without requiring physical development boards.
